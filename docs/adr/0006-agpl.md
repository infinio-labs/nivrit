# 0006 — AGPL-3.0-only

**Status:** Accepted (2026-07-27)

## Context

Nivrit is a secret manager whose central claim is that the server cannot read
your secrets. That claim is only meaningful if you can verify the code that is
actually running — both the server you connect to and, more importantly, the
frontend it serves you, since that frontend holds your decrypted keys.

A permissive licence (MIT, Apache-2.0) allows anyone to run a modified,
closed-source Nivrit as a hosted service. A modified frontend that exfiltrates
keys is indistinguishable from an honest one to the user. The licence is
therefore not only a business decision here; it is part of what makes the
security claim auditable.

## Decision

AGPL-3.0-only for the whole project: crates, web client, SDKs, and extension.

## Consequences

**Hosted modifications must be published.** The AGPL's network clause is the
point: anyone offering Nivrit as a service must offer the corresponding source,
including their frontend changes. A user of a hosted instance can therefore, in
principle, verify what they are running. Under a permissive licence they could
not, and "zero-knowledge" would rest entirely on the operator's word.

**This deters some commercial adoption**, which is the main cost. Companies with
policies against AGPL dependencies will not embed Nivrit. We accept that: Nivrit
is a self-hosted application, not a library meant to be linked into other
products.

**The SDKs are affected too, and this deserves care.** They are AGPL, which is
unusual for a client library and may deter exactly the integrations that make the
product useful. If SDK adoption proves to be the bottleneck, relicensing *only*
the SDKs — which contain no cryptographic implementation, just HTTP calls and
subprocess invocation — under Apache-2.0 or MPL-2.0 is a reasonable future
decision. It would not weaken the argument above, because the auditability that
matters concerns the server and the frontend, not the client wrappers.

**"only", not "or-later".** `AGPL-3.0-only` fixes the terms rather than accepting
whatever a future AGPL-4.0 might say. Contributors and users get certainty about
which licence governs.

**Dependency licences must stay compatible.** AGPL-3.0 can absorb MIT, Apache-2.0
and similar permissive licences, but the reverse is not true and some copyleft
licences conflict. `cargo deny check licenses` enforces this in CI against an
explicit allowlist, so an incompatible transitive dependency fails the build
rather than being discovered at release.

## Rejected alternatives

**MIT or Apache-2.0.** Maximum adoption, and no way for a user of a hosted
instance to verify the code holding their keys. Rejected for the reason above.

**Business Source Licence or similar source-available terms.** Would protect
against commercial hosting while allowing inspection, but is not open source,
would exclude Nivrit from distributions and many corporate environments, and
trades away the community contribution the project wants.
