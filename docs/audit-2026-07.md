# Nivrit pre-release audit — 2026-07-27

> **Status: remediated.** Every finding below was fixed on branch
> `agent/pre-release-audit-fixes` (commits `db5871b`, `f73fe86`, and the docs
> and supply-chain commit that follows them). The report is kept as written, in
> its original assessment voice, as the record of what was found and why — see
> `CHANGELOG.md` for what shipped. The one item deliberately **not** actioned is
> the suggestion under "On the smallest minimalist goal": the README already
> scopes the non-Node SDKs as experimental, so no code was removed.

Scope: full codebase at `3e5c388` (branch `agent/self-hosted-actions`). Rust workspace
(8 crates, ~11.3k LOC), React/TypeScript web client (~4.5k LOC), VS Code extension,
and seven language SDKs. Reviewed for open-source-release readiness, per-language
best practice, security, and performance.

Verdict: the engineering quality is high — pinned dependencies, no `unsafe`, compile-time
checked SQL, clippy at `-D warnings`, a clean `cargo audit`, meaningful crypto tests, and
an honest "pre-audit" disclaimer already in the docs. One architectural finding
(P0-1) contradicts the project's central claim and should be fixed or the claim
restated before the repo goes public. The rest are ordinary hardening items.

## P0 — release blockers

### P0-1. The master password is sent to the server in plaintext; this defeats zero-knowledge

`README.md:30` states "The backend never has the keys or the plaintext" and
`docs/architecture.md:68` lists "Malicious server operator: cannot read secret values
without project keys" as protected-against. Neither holds.

Four endpoints receive the user's master password as a plaintext JSON field:

| Endpoint | Field | Location |
|---|---|---|
| `POST /auth/register` | `password` | `crates/nivrit-api/src/handlers/auth.rs:98` |
| `POST /auth/login` | `password` | `crates/nivrit-api/src/handlers/auth.rs:163` |
| `POST /auth/oauth/setup` | `master_password` | `crates/nivrit-api/src/handlers/auth.rs:385` |
| `POST /auth/reset-password` | `new_password` | `crates/nivrit-api/src/handlers/auth.rs:515` |

The same password derives the KEK that wraps the user's hybrid private key
(`crates/nivrit-auth/src/user_keys.rs:8`). So a server that holds the password holds the
private key, hence every project DEK, hence every secret value. `register` makes this
explicit — it decrypts the user's private key server-side
(`crates/nivrit-api/src/handlers/auth.rs:118`) so it can build the recovery blob, meaning
the plaintext hybrid private key is in server memory during registration.

The at-rest property ("the database stores only ciphertext") is real and intact. The
zero-knowledge property against the *operator* is not: a malicious or compromised server
captures every password on the way in, with a one-line change no client can detect.

**Fix (the standard split-derivation pattern):** the client derives two independent
values from the master password and sends only the first.

```
authHash = Argon2id(password, salt, info="nivrit-auth-v1")   -> sent to server
encKey   = Argon2id(password, salt, info="nivrit-enc-v1")    -> never leaves the client
```

The server stores `Argon2id(authHash)` in `users.password_hash` and treats `authHash` as
an opaque credential. Registration recovery material must move client-side too: the client
generates the recovery code, derives the recovery key, encrypts its own private key under
it, and uploads only the ciphertext plus the code hash — the server never sees the code or
the plaintext key. The crypto-helper and WASM module already expose everything needed for
this; it is a protocol change, not new primitives.

**If you'd rather not do this before v0.1:** say so plainly. Replace the "malicious server
operator" bullet with the truth — Nivrit protects against database compromise and network
interception, and against a *passive* operator, but an active operator who modifies the
server can capture passwords. Shipping the current claim as written is the kind of thing a
security reviewer will lead with.

### P0-2. Every published URL points at the wrong GitHub org

`git remote` is `github.com/infinio-labs/nivrit`. `Cargo.toml:20` agrees. Fourteen other
files say `infiniolabs` (no hyphen):

`README.md`, `SECURITY.md`, `CHANGELOG.md`, `deploy/docker-compose.yml`,
`.github/ISSUE_TEMPLATE/config.yml`, `extensions/vscode/package.json`,
`sdks/node/package.json`, `sdks/python/pyproject.toml`, `sdks/java/pom.xml`,
`sdks/elixir/mix.exs`, `sdks/rust/README.md`, `sdks/go/nivrit/README.md`,
`sdks/elixir/README.md`.

Consequences: the vulnerability-reporting link in `SECURITY.md` 404s, the GHCR image
references in `deploy/docker-compose.yml` point at a non-existent org, and every SDK
published to npm/PyPI/Maven/Hex carries a dead repository URL that cannot be corrected
after publication without a version bump. Pick one spelling and sweep.

### P0-3. Five links to a deleted `ROADMAP.md`

`ROADMAP.md` was deleted in `41ed44b`, but is still linked from `README.md` (three places,
including the "supported surface" caveat), `docs/architecture.md:55`, and
`sdks/PUBLISHING.md:6`. Two of those links carry load-bearing caveats about what is
supported and when the audit lands. Either restore the file or inline the content.

## P1 — security

### P1-1. Unauthenticated registration is a memory-exhaustion DoS

`POST /auth/register` requires no authentication, no rate limit, and no CAPTCHA, and each
call performs **four** Argon2id operations at 64 MiB each: `hash_password`,
`derive_key` (inside `decrypt_private_key_with_password`), `derive_recovery_key`, and
`hash_recovery_code`. That is ~256 MiB of resident memory and several hundred milliseconds
of CPU per unauthenticated request.

Compounding it: no call site anywhere in the workspace uses `tokio::task::spawn_blocking`
(verified by grep). Argon2 runs directly on the multi-threaded Tokio runtime, so N
concurrent registrations block N runtime workers and starve every other in-flight request,
including the `/ready` healthcheck.

Fixes, in order of value: wrap every Argon2 call in `spawn_blocking`; rate-limit
`/auth/register` on source IP with the existing `LoginRateLimiter`; and move recovery-blob
construction to the client (which P0-1 requires anyway) to cut four Argon2 calls to one.

### P1-2. Login throttling is bypassed by rotating source IPs

The rate-limit key is `format!("{}|{}", req.email, addr.ip())`
(`crates/nivrit-api/src/handlers/auth.rs:170`). The comment explains the intent — one IP
must not be able to lock a victim's account — which is correct. But the consequence is
that there is *no* per-account limit at all: an attacker with a botnet or a rotating proxy
gets unlimited guesses against a single account, because every new IP is a fresh bucket.

Standard resolution is two independent counters: a strict per-`ip` limit (blocks a single
noisy source) plus a looser per-`email` limit that throttles rather than hard-locks
(exponential delay, or a lock that requires an emailed unlock link). Also note `addr.ip()`
is the socket peer — behind the bundled nginx proxy that is the proxy's IP, so the limiter
currently sees one key for all users. Parse `X-Forwarded-For` (trusting only your own
proxy hop) or document that the API must not be deployed behind an un-configured proxy.

### P1-3. No key material is ever zeroized

`zeroize` is not a dependency of any crate (verified by grep across `crates/`). Every
secret-bearing value — derived KEKs (`nivrit-crypto/src/password.rs:20`), the 32-byte
project keys, `HybridUserKeyPair`'s X25519 secret and ML-KEM seed, passwords as `String`,
and the plaintext private keys in `nivrit-crypto-helper` — is dropped without being
scrubbed and lingers in freed heap until overwritten.

For a secret manager this is table stakes: it is what makes a core dump, a swap file, or a
heap-spray read leak nothing instead of everything. Add `zeroize` with the `derive`
feature and apply `ZeroizeOnDrop` to `HybridUserKeyPair`, the derived-key return types,
and the helper's decoded buffers. `x25519-dalek`'s `StaticSecret` already zeroizes itself;
the rest do not.

### P1-4. The CLI writes plaintext private keys to disk with default permissions

`crates/nivrit-cli/src/main.rs:606` writes `~/.nivrit/config.json` via `std::fs::write`,
which creates the file 0666-and-umask — 0644 on a typical Linux box, world-readable. The
file contains `private_key` (the base64 plaintext hybrid private key, set at
`main.rs:697` and `main.rs:789`) and `project_keys` (plaintext project DEKs, `main.rs:831`
— note the `nonce` field is written as an empty string, confirming these are not
encrypted). Any local user or any process running as the user reads every secret in every
project.

Minimum fix: `OpenOptions::new().mode(0o600)` on Unix, and `create_dir_all` the `.nivrit`
directory at 0700. Better: derive a session key and encrypt the cached keys at rest, or
hand them to the platform keyring — the VS Code extension already does the right thing by
using `vscode.SecretStorage` (`extensions/vscode/src/session.ts:19`).

### P1-5. TOTP can be re-enrolled with only a stolen session token

`setup_totp` (`crates/nivrit-api/src/handlers/auth.rs:605`) requires only `CurrentUser`,
and unconditionally overwrites any existing TOTP secret. `disable_totp` correctly demands
the password *and* a current code; `setup_totp` demands neither. An attacker holding a
hijacked JWT or a leaked PAT re-enrolls their own authenticator and the second factor is
gone. Require password re-authentication when a TOTP secret already exists.

### P1-6. `NIVRIT_CRYPTO_HELPER` redirects crypto to an arbitrary binary

Every non-Rust SDK resolves the helper from `$NIVRIT_CRYPTO_HELPER` first
(`sdks/node/src/crypto.js:6` and its siblings), then falls back to the bundled platform
package. The master password is written to that process's stdin. Anyone who can set an
environment variable in the target process — a CI config, a `.envrc`, a compromised
dependency's postinstall — silently harvests passwords and private keys.

The escape hatch is legitimately useful for development, so rather than removing it:
document it as a trust boundary in `SECURITY.md`, and consider verifying the bundled
helper's hash when the override is *not* set.

## P2 — correctness and robustness

### P2-1. `rotate_key` is not transactional and leaves the recovery blob stale

`crates/nivrit-api/src/handlers/users.rs:162`. The user's keypair is updated first, then
project keys are rewritten one at a time in a loop, each with its own round trip. A
failure — a dropped connection, a membership check that errors, the 30-second request
timeout — halfway through the loop leaves the account with a new keypair while some
project keys are still wrapped to the *old* public key. Those projects become permanently
undecryptable, since the old private key is gone from both server and client. Wrap the
whole operation in one `sqlx` transaction.

Separately, rotation never touches `encrypted_private_key_recovery`. After a rotation the
recovery blob still holds the pre-rotation private key, so `reset_password`
(`handlers/auth.rs:556`) restores a stale key and silently locks the user out of every
project whose key was rotated. The rotation request needs to carry a re-encrypted recovery
blob too.

### P2-2. `disable_totp` can panic on a short blob

`crates/nivrit-api/src/handlers/auth.rs:668` calls `blob.split_at(12)` with no length
check. The two sibling call sites — `login_totp:238` and `verify_totp:636` — both check
`blob.len() < 12 + 16` first. `split_at` panics when `mid > len`, which in an Axum handler
means a dropped connection and a poisoned task. Not currently reachable (the blob is
always written by `setup_totp`), but it is one bad migration away from being a remote
panic. Add the same guard.

### P2-3. No pagination on any list endpoint

`list_secrets` (`crates/nivrit-db/src/queries.rs:510`), `list_secret_versions`,
`list_personal_access_tokens`, `list_folders`, and `list_user_projects` all `fetch_all`
with no `LIMIT`. Only the audit-log query has one (`queries.rs:1065`). A project with many
secrets, or a long-lived secret with a deep version history, produces an unbounded
response body and an unbounded server-side allocation. Add cursor pagination before the
API is public and callers start depending on the unpaginated shape.

### P2-4. The recovery KDF is weaker and inconsistent with the rest of the code

`crates/nivrit-auth/src/recovery.rs` uses `Argon2::default()` (19 MiB, t=2) for both
`hash_recovery_code` and `derive_recovery_key`, while `nivrit-crypto/src/password.rs` and
`nivrit-auth/src/password.rs` both use a deliberate 64 MiB / t=3. It also derives the
recovery key with a single global salt, `RECOVERY_SALT = b"nivrit-recovery-v1"`
(`recovery.rs:12`), shared across all users.

The global salt is defensible — recovery codes carry ~120 bits of entropy, so
precomputation is infeasible regardless — but it is a gratuitous deviation from
best practice, and the security argument now rests entirely on the code generator staying
strong. Using `user_id` as the salt costs nothing. (The generator itself is sound: 24
bytes reduced mod a 32-character alphabet, and 256/32 divides evenly, so there is no
modulo bias.)

### P2-5. `.claude/settings.local.json` is only ignored by your personal global gitignore

`git check-ignore` resolves it to `/home/sid/.config/git/ignore`, not the repo's
`.gitignore`. On any other contributor's machine it is untracked-and-offered. Add
`.claude/`, `.codex/`, and `.agents/` to the repo `.gitignore` before opening the repo up.

## Performance

The hot paths are in good shape: `lto = true` and `opt-level = 3` are set, the sqlx pool
is bounded with a 5-second acquire timeout, request bodies are capped at 1 MiB, there is a
30-second request timeout, and Prometheus metrics are already wired in. Four items:

1. **Argon2 on the async runtime** (see P1-1) — the single largest throughput risk. Every
   password operation blocks a Tokio worker for hundreds of milliseconds.
2. **Two DB round trips on every authenticated request.** `CurrentUser`
   (`crates/nivrit-api/src/auth.rs:44`) does a user lookup per request, and the PAT path
   adds a `tokio::spawn`'d `last_used_at` write per request. At load that write becomes a
   hot-row contention point on `personal_access_tokens`. Batch it — update at most once per
   minute per token, or buffer and flush.
3. **Helper process spawn per crypto call.** Each SDK operation is a fresh `spawnSync`
   (`sdks/node/src/crypto.js:30`). Process creation plus a 64 MiB Argon2 per call makes
   bulk operations expensive. A long-lived helper speaking newline-delimited JSON would be
   a drop-in improvement to the same protocol.
4. **Binary size**, given the "smallest" goal: adding `codegen-units = 1`, `panic = "abort"`,
   and `strip = "symbols"` to `[profile.release]` typically takes 30-40% off the CLI and
   helper binaries. `panic = "abort"` is safe here — nothing catches unwinds.

## Per-language best-practice check

**Rust (8 crates, ~11.3k LOC) — strong.** Exact-pinned dependency versions throughout,
`Cargo.lock` committed with a comment explaining why, `cargo clippy --locked --workspace
--all-targets -- -D warnings` in CI, `cargo audit` in CI (clean at time of audit — 479
dependencies, zero advisories), `cargo fmt --check`. No `unsafe` anywhere. All SQL goes
through `sqlx::query!`/`query_as!` macros, verified at compile time against a live schema
and checked in as `.sqlx` offline metadata — injection is structurally impossible. Errors
are a proper `thiserror` enum, and `ApiError::into_response`
(`crates/nivrit-api/src/error.rs:20`) correctly logs internal detail server-side while
returning a generic message, so DB and crypto internals never leak to clients. Test
coverage of the crypto and auth crates is genuinely good, including wire-format stability
vectors (`suite.rs:187`, `jwt.rs:78`) that will catch an accidental breaking change to the
on-disk format. Gaps: no `#![forbid(unsafe_code)]` at any crate root (cheap, and it
documents intent); no `cargo-deny`, so license compatibility and duplicate/yanked crates
go unchecked — worth adding alongside `cargo audit` given AGPL distribution; and the
`zeroize`/`spawn_blocking` gaps noted above.

**TypeScript / React — strong.** `strict: true` plus `noUnusedLocals`,
`noUnusedParameters`, and `noFallthroughCasesInSwitch`. Vitest for units, Playwright for
e2e, `bun install --frozen-lockfile` in CI. No `dangerouslySetInnerHTML`, no `innerHTML`,
no `eval` anywhere in the web or extension source. The bearer token is deliberately kept
in memory rather than `localStorage`, with a comment explaining the XSS reasoning
(`crates/nivrit-web/src/session.ts:92`) — exactly right for an E2EE app, and the nginx CSP
that backs it up (`nginx.web.conf:14`) is well-constructed, including
`frame-ancestors 'none'` and `base-uri 'none'`. One gap: `crypto.ts` selects the WASM
build by reading `process.env.NODE_ENV === 'test'` in what is otherwise browser code;
that works via the `process.d.ts` shim but is fragile — prefer `import.meta.env.MODE`.

**Python / Ruby / Elixir / Java / Go / .NET SDKs — thin and consistent.** All six are
subprocess wrappers around one Rust binary, which is the right call: one audited crypto
implementation rather than six. Passwords go over stdin rather than argv, so they never
appear in `ps` output — a detail that is easy to get wrong and was gotten right. The
helper-discovery logic is duplicated near-identically across all six; that is acceptable
for ~15 lines each. Concerns are the `NIVRIT_CRYPTO_HELPER` trust boundary (P1-6) and
process-spawn cost (Performance #3).

**CI/CD — above average.** Every GitHub Action is pinned to a full commit SHA with a
version comment, Docker base images are pinned by digest, and even apt packages are
version-pinned in `Dockerfile.api`. The release workflow pins a rebar3 SHA-512. That is
more supply-chain discipline than most projects at 1.0. Two notes: the API Dockerfile
never creates a non-root user, so `nivrit-api` runs as root in the container — add a
`USER` directive; and the self-hosted-runner conditional
(`github.event.repository.private && 'self-hosted'`) is a clean trick, but confirm the
runner is ephemeral before the repo goes public, since a public repo with a persistent
self-hosted runner is a fork-PR code-execution risk. As written the expression flips to
`ubuntu-24.04` on publication, which is correct — just make sure that happens atomically
with the visibility change.

## On the "smallest minimalist" goal

The Rust core is genuinely minimal and I would not cut anything from it. The surface area
that fights the goal is the periphery: seven SDKs, a VS Code extension, and a full React
web UI, all pre-1.0, pre-audit, and each needing a per-platform helper binary matrix on
every release. That is a large ongoing maintenance and security surface for a project
whose differentiator is the crypto core.

Suggestion for v0.1: ship the API, CLI, Rust SDK, and web UI as supported; label the other
six SDKs and the extension explicitly experimental and community-maintained. The README
already gestures at this distinction — make it a hard line, and the release surface drops
by more than half without removing a single feature.

## Suggested order of work

1. Decide P0-1: implement split derivation, or restate the claim. Everything else is
   smaller than this one decision.
2. P0-2 and P0-3 — mechanical, an hour, and both are visible on day one of the repo
   being public.
3. P1-1 through P1-4 — `spawn_blocking`, registration rate limit, `zeroize`, CLI file
   permissions. Each is self-contained.
4. P2-1 (the rotation transaction) before anyone rotates a key in anger.
5. The rest as normal backlog.
